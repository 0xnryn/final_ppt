Eliminating Black-Box Non-Determinism

Problem Statement & Core Pipeline

Why Standard LLMs Fail Audits

1. Non-Deterministic Execution: Parallel GPU reductions alter floating-point addition order, yielding different tokens for identical prompts.

2. Zero Tamper Proof: Plain-text AI responses carry no cryptographic proof of origin or integrity.

The cvdllm Solution

1. Deterministic CPU Engine: Single-threaded inference with greedy decoding locks execution order.

2. Canonical SHA-256 + TPM 2.0: Output is serialized canonically and signed inside isolated TPM silicon.

Architectural Migration & Engineering Trade-offs

From Cactus Needle 2 to Qwen 2.5 (0.5B)

Phase 1 Prototype: Cactus Needle 2

• Ultra-Lightweight Footprint (~14 MB): Enabled fast initial validation (~500 words/sec) of single-thread greedy decoding.

• Key Limitations: Narrow general-purpose reasoning, limited context coherence, and restricted ecosystem support for standardized GGUF quantization and LoRA merging.

Why We Switched to Qwen 2.5-0.5B-Instruct

• Superior Instruction Following: 0.5B parameters deliver coherent, reliable answers while remaining CPU-friendly (~400 MB q4_k_m).

• Standardized GGUF & llama-cpp-python: Explicit thread locking (n_threads=1), deterministic seed control, and seamless LoRA-to-GGUF weight merging.

04 · Cryptography & AttestationVedant

Canonical Serialization & Hardware Signing

SHA-256 Canonicalization & TPM Signing

Step 1: Canonical Semantic Hashing

The inference payload is canonically serialized into JSON with alphabetically sorted keys and hashed via SHA-256 to produce a unique 32-byte fingerprint.

Volatile runtime metrics (RAM, tokens/sec) are excluded. sort_keys=True guarantees identical byte order regardless of dictionary insertion order.

Step 2: Hardware-Bound Signature

The TPM 2.0 security chip signs the SHA-256 digest directly inside isolated hardware using its unexportable private key.

The 32-byte SHA-256 digest is passed to TPM 2.0 via tpm2_sign, producing a non-repudiable RSA-2048 signature.

  • Key Provisioning (tpm/create.py)Generates primary & RSA signing keys inside TPM and persists handle 0x81010002.
  • Digest Signing (tpm/sign_hash.py)Converts hex SHA-256 to binary digest and signs inside TPM silicon.
  • Public Key Export (tpm/read_public.py)Exports PEM RSA public key so external auditors can verify receipts offline.
04 · Cryptography Deep DiveVedant

Security Guarantees & Trust Model

How Cryptography Secures cvdllm

SHA-256 Integrity & Avalanche Effect

Tamper Detection: Every generated response is distilled into a fixed 256-bit cryptographic digest.

Altering even a single character, whitespace, or punctuation mark in the prompt or LLM output completely changes the resulting hash, immediately exposing any post-inference manipulation.

RSA-2048 Asymmetric Signing

Hardware-Locked Private Key: Generated inside the TPM 2.0 chip at handle 0x81010002, the private key is never exposed to RAM, disk, or the OS.

Public Key Distribution: The corresponding public key is freely exported in PEM format so any third party can validate authenticity.

Zero-Trust Offline Verification

• 1. Recompute Digest: The auditor canonically serializes the received JSON output and calculates its SHA-256 hash locally.

• 2. Validate Signature: verify_signature.py uses OpenSSL and the exported TPM public key to verify the RSA-2048 signature against the digest.

• 3. Non-Repudiation: A valid match proves the exact output originated from that specific physical TPM hardware and has remained untouched since generation.

Why Parallel Hardware Breaks Reproducibility

Floating-Point Associativity Invariant

IEEE-754 Non-Associativity & Single-Thread Reduction

$$(a + b) + c \;\neq\; a + (b + c)$$

In multi-threaded GPU kernels, dynamic warp scheduling alters floating-point accumulation order across parallel cores. Even tiny rounding differences at the lowest bit shift output logits and cascade into diverging token sequences across runs.

Enforcing sequential single-thread CPU reduction locks a strict, invariant addition tree—guaranteeing bit-identical floating-point sums, identical logits, and the exact same generated tokens on every execution.

Closing the Gap Between Execution & Attestation

How Determinism and TPM Work Together

Why TPM Alone Isn't Enough

A TPM signature proves who signed an output and that it wasn't altered afterward—but if the LLM runs non-deterministically, re-running the same prompt yields a completely different hash, making independent verification impossible.

Why Determinism Alone Isn't Enough

Single-thread CPU execution guarantees the same prompt always produces the exact same text, but without hardware signing, anyone can forge or edit a plain-text log after the fact.

Combined Verifiable Proof

• 1. Reproducible Digest: Deterministic execution ensures any auditor running the same model and prompt arrives at the exact same canonical SHA-256 hash.

• 2. Hardware-Bound Receipt: TPM 2.0 signs that digest with an unexportable RSA-2048 key, binding the reproducible output to physical silicon.

• 3. Replay + Tamper Proof: Auditors can both verify the cryptographic signature offline and re-execute the prompt to confirm bit-exact provenance.
